## 1. 프로젝트 개요

### 서비스 소개

TALKI는 발표 불안을 겪는 사용자가 실제 환경과 유사한 조건에서 반복 연습하고, AI 기반 분석을 통해 즉각적인 피드백을 받을 수 있는 웹 서비스입니다.

발표가 끝나면 시선 처리, 자세 안정성, 발화 속도, 주제 적절성, 추임새 빈도 등 5개 항목이 정량적으로 측정되어 리포트 형태로 제공됩니다. 사용자는 본 실전에 앞서 즉흥 말하기, 키워드 구성, 핵심 파악 등 단계별 연습 모드를 통해 충분히 준비할 수 있습니다.

### 기획 배경

발표 준비가 어려운 가장 큰 이유는 **"혼자서 연습할 환경"** 과 **"객관적인 피드백"** 이 없기 때문입니다. TALKI는 상황별 배경 영상(화상 회의, 강당, 강의실 등)으로 실제 환경을 재현하고, AI가 실시간으로 분석한 데이터를 기반으로 구체적인 개선 방향을 제시합니다.

### 나의 역할

전체 서비스에서 사용자와 직접 맞닿는 7개 주요 화면을 담당했습니다.

| 담당 영역 | 주요 내용 |
|-----------|-----------|
| 메인 랜딩 페이지 | 서비스 소개 및 진입 UI, 스크롤 인터랙션 |
| 홈 대시보드 | 연습 이력, 스트릭, 최근 리포트 요약 |
| 실시간 실전 페이지 | 카메라·음성·WebSocket 통합 실전 화면 |
| 분석 결과 세부 페이지 | 5개 섹션 시각화, 영상 타임스탬프 리뷰 |
| 연습 모드 3종 | 즉흥 말하기 / 키워드 구성 / 핵심 파악 |

### 서비스 전체 흐름

```
랜딩 → 회원가입/로그인 → 홈 대시보드
  → 카테고리 설정(발표 유형·주제) → 환경 점검(카메라·마이크)
  → 실전 발표(실시간 분석) → 영상 업로드 → 분석 대기
  → 기본 결과 리포트 → (프리미엄) 세부 분석
```

## 2. 기술 스택

### 선택 기준

기술 스택 선택에서 가장 중점을 둔 것은 **브라우저에서 실시간으로 카메라·음성 데이터를 처리**해야 한다는 요구사항이었습니다. 서버 왕복 없이 클라이언트에서 직접 분석 데이터를 생성하고 WebSocket으로 전송하는 구조가 필요했기 때문에, 브라우저 네이티브 API를 충분히 지원하는 환경이 전제였습니다.

| 분류 | 기술 | 선택 이유 |
|------|------|-----------|
| UI 프레임워크 | React 19 + TypeScript | 컴포넌트 재사용성, 타입 안전성 |
| 빌드 | Vite 7 | 빠른 HMR, `@/` 경로 별칭, API 프록시 설정 |
| 스타일링 | Tailwind CSS 3 | 반응형 레이아웃 빠른 구현 |
| 컴퓨터 비전 | MediaPipe FaceMesh + Pose | 브라우저 WASM 기반, 서버 불필요 |
| 미디어 처리 | MediaRecorder + Web Audio API | 영상 녹화·오디오 분석 네이티브 지원 |
| 실시간 통신 | WebSocket | 낮은 지연 시간의 양방향 데이터 전송 |
| 차트 | Recharts + 순수 SVG | 일반 차트는 Recharts, 특수 레이더는 직접 구현 |
| PDF 생성 | html2canvas + jsPDF | 결과 화면을 그대로 PDF로 변환 |
| 라우팅 | React Router DOM 7 | SPA 기반 페이지 전환 |

### 3.1 메인 랜딩 페이지

> 📸 _[랜딩 페이지 전체 스크린샷]_

#### 무엇을 만들었는가

서비스의 첫인상을 결정하는 랜딩 페이지 전체를 구현했습니다. Hero, 사용자 고민 공감, 기능 소개, 요구사항, FAQ, CTA 총 7개 섹션으로 구성되며, 스크롤에 따라 콘텐츠가 자연스럽게 드러나는 구조입니다.

#### 스크롤 기반 카드 펼침 인터랙션

기능 소개 섹션에서는 쌓여 있던 카드들이 스크롤에 비례해 순서대로 펼쳐지는 인터랙션을 구현했습니다. 단순한 fade-in이 아닌, **사용자의 스크롤 속도가 곧 애니메이션 속도가 되는** 방식을 선택한 이유는 사용자가 콘텐츠를 자신의 페이스로 탐색할 수 있게 하기 위함이었습니다.

구현 핵심은 세 단계입니다. 첫째, 렌더링 직후 각 카드의 실제 높이를 측정해 카드가 완전히 펼쳐졌을 때의 목표 위치를 계산합니다. 둘째, 스크롤 이벤트마다 섹션의 뷰포트 내 위치를 0~1 사이의 `progress` 값으로 정규화합니다. 셋째, 각 카드가 독립적인 progress 구간에서 이동하도록 분할하여 순차적으로 펼쳐지는 효과를 만들었습니다. 위치 보간에는 `easeOutCubic`을 적용해 카드가 자리에 안착하는 느낌을 강조했습니다.

#### 스크롤에 따른 네비게이션 전환

Hero 섹션이 지나가면 투명 배경의 메인 네비게이션에서 흰 배경의 일반 네비게이션으로 자연스럽게 교체됩니다. 보이지 않는 sentinel 요소의 뷰포트 위치를 스크롤 이벤트마다 측정해 전환 시점을 판단했습니다.

#### 사용자에게 제공한 가치

단순 텍스트 나열이 아닌, 스크롤 흐름 속에서 서비스 기능이 자연스럽게 소개되어 랜딩 페이지 체류 시간을 높이고 서비스에 대한 기대감을 형성합니다.

### 3.2 메인 홈 대시보드

> 📸 _[홈 대시보드 스크린샷]_

#### 무엇을 만들었는가

로그인 후 진입하는 메인 화면으로, 사용자의 연속 연습 스트릭, 이번 주 연습 이력, 마음가짐 기록, 최근 발표 리포트 요약을 한눈에 볼 수 있는 대시보드입니다. 우측에는 월별 캘린더 뷰와 성장 그래프 뷰를 토글로 전환할 수 있습니다.

#### 설계 방향

데이터가 2개의 독립적인 API에서 제공됩니다. 사용자 닉네임은 `/profile/get`, 연습 이력과 리포트는 `/personal/home`에서 각각 가져옵니다. 두 API를 하나의 useEffect로 묶지 않고 별도로 분리한 이유는 **하나의 API가 실패해도 나머지 정보는 정상 표시**되어야 한다는 원칙 때문입니다.

#### 데이터 처리

서버에서 날짜를 `"YYYY-MM-DD"` 문자열로 내려주는데, 이를 `new Date("YYYY-MM-DD")`로 파싱하면 UTC 기준으로 처리되어 한국 시간 기준의 날짜와 불일치가 생깁니다. 연·월·일을 직접 분리해 `new Date(y, m-1, day)`로 생성해 로컬 타임존 기준으로 변환했습니다.

#### 반응형 레이아웃

모바일에서는 주요 기능 진입 버튼이 하단에, 데스크톱에서는 좌측 사이드 패널(1/3)과 우측 콘텐츠 영역(2/3)으로 분리됩니다. CSS `order` 속성으로 모바일과 데스크톱의 시각적 순서를 다르게 처리했습니다.

### 3.3 실시간 실전 페이지

> 📸 _[실시간 실전 화면 스크린샷]_

#### 무엇을 만들었는가

서비스의 핵심 기능입니다. 사용자가 카메라 앞에서 발표하는 동안 세 가지가 동시에 진행됩니다.

- **MediaPipe**가 매 프레임 얼굴 랜드마크(468개)와 자세 랜드마크(33개)를 추출
- **Web Audio API**가 마이크 오디오를 1초 단위로 수집·변환하여 WebSocket으로 전송
- **MediaRecorder**가 발표 전체를 영상 파일로 녹화

#### 컴포넌트 설계 철학

화면에 카메라 피드를 보여주지 않는 `LiveFeedbackTracker` 컴포넌트가 위 세 가지 처리를 모두 담당합니다. 부모 컴포넌트에는 `stopRecording()` 함수 하나만 노출하고 내부 복잡도는 완전히 감춥니다. 이렇게 설계한 이유는 실전 화면 UI(토글, 피드백 메시지, 종료 버튼)와 미디어 처리 로직이 서로 의존하지 않아야 유지보수가 쉽기 때문입니다.

매 프레임마다 갱신되는 얼굴·자세 데이터는 React state 대신 ref로 관리했습니다. state로 관리할 경우 초당 30회 이상 리렌더링이 발생하므로 UI 성능에 영향을 주기 때문입니다.

#### 영상 업로드 흐름

종료 버튼을 누르면 녹화된 영상 Blob을 서버에서 발급받은 S3 Presigned URL로 직접 PUT 업로드합니다. 파일을 서버를 거치지 않고 스토리지에 바로 올리는 방식을 선택한 이유는 서버 부하를 줄이고 업로드 속도를 높이기 위함입니다.

#### 카운트다운과 녹화의 분리

5초 카운트다운은 사용자가 자세를 잡는 준비 시간입니다. 이 시간이 녹화에 포함되면 분석 정확도가 떨어집니다. 카메라 초기화와 녹화 시작을 분리하여, 카운트다운이 완전히 끝난 시점에만 녹화를 시작하도록 설계했습니다. (→ 트러블슈팅 참고)

### 3.4 실시간 분석 세부 결과 페이지

> 📸 _[분석 결과 세부 페이지 스크린샷]_

#### 무엇을 만들었는가

발표 종료 후 AI가 산출한 5개 항목의 정량 점수와 LLM 생성 텍스트 피드백을 시각화하는 페이지입니다. 기본 분석(무료)과 세부 분석(프리미엄)으로 나뉩니다.

세부 분석은 음성 분석, 시선 분석, 행동 분석, 발표 내용 분석, 전체 분석 5개 섹션으로 구성됩니다.

#### 시각화 요소

**① 원형 진행률 차트 (CircleProgress)**
4개 항목(발화 속도·시선 집중도·주제 적절성·제스처 안정성)을 원형 SVG로 표현합니다. 40점 미만은 빨간색, 70점 미만은 주황색, 70점 이상은 초록색으로 구분되며, 점수가 1.5초에 걸쳐 애니메이션으로 올라갑니다. 숫자가 바뀌는 것을 보여주는 것만으로도 사용자가 자신의 점수에 집중하게 만드는 효과가 있습니다.

**② WPM 바 차트**
발화 속도를 0~200 WPM 트랙 위에 현재 위치로 표시합니다. 120~160 WPM의 적정 구간을 초록색으로 강조해, 사용자가 자신이 너무 빠른지 느린지를 직관적으로 파악할 수 있습니다.

**③ 삼각형 레이더 차트 (TriangleChart)**
시선 집중도·제스처 안정성·주제 적절성 3개 항목을 정삼각형 레이더 차트로 시각화합니다. 기존에는 정적 이미지 파일로 대체되어 있었는데, 실제 점수 데이터를 반영하는 SVG 컴포넌트로 교체했습니다. 삼각법(cos/sin)으로 꼭지점 좌표를 계산하고 점수 비율로 스케일링하여 순수 SVG만으로 구현했습니다.

#### 섹션 지연 렌더링

5개 섹션이 한꺼번에 렌더링되면 페이지 진입 시 무겁게 느껴집니다. IntersectionObserver로 각 섹션이 뷰포트에 20% 이상 진입했을 때 `translate-y-10 opacity-0` → `translate-y-0 opacity-100` CSS 전환을 적용해, 스크롤 내리는 흐름에 맞춰 자연스럽게 나타나도록 했습니다.

#### 영상 타임스탬프 리뷰

약점 구간과 돌발 질문이 발생한 타임스탬프를 목록으로 보여주고, 클릭 시 해당 시점으로 영상이 이동합니다. 사용자가 발표 영상을 처음부터 끝까지 돌려보지 않아도 핵심 구간만 빠르게 확인할 수 있도록 설계했습니다.

### 3.5 연습 모드 3종 (즉흥 말하기 / 키워드 구성 / 핵심 파악)

> 📸 _[연습 모드 화면 스크린샷]_

#### 무엇을 만들었는가

실전에 앞서 말하기 근육을 키우는 3가지 연습 모드를 구현했습니다. 세 모드 모두 동일한 4단계 흐름(`idle → preparing → recording → finished`)을 공유하며, 각 모드는 고유한 콘텐츠와 피드백 방식을 가집니다.

| 모드 | 콘텐츠 | 특징 |
|------|--------|------|
| 즉흥 말하기 | 3개 주제 중 무작위 1개 출제 | 주제를 보고 10초 준비 후 30초 발표 |
| 키워드 구성 | 3개 키워드 제시 | 키워드를 모두 포함하여 자유 발표 |
| 핵심 파악 | 긴 지문 제시 | 지문의 핵심을 3개 키워드로 요약 발표 |

#### 설계 핵심 — 공통 레이아웃 컴포넌트

3개 연습 모드가 다른 팀원이 만든 다른 연습 기능과 나란히 존재하는 구조입니다. UI 일관성을 유지하면서 각 모드의 콘텐츠는 독립적으로 교체할 수 있도록 `PracticeLayout` 공통 컴포넌트를 설계했습니다. 사이드바 스텝 인디케이터, 탐색 잠금, 이전/다음 버튼이 모두 이 컴포넌트에 캡슐화되어 있습니다.

연습 중에는 페이지 이탈을 막는 `isLocked` prop이 활성화됩니다. 사용자가 실수로 다음 버튼을 눌러 연습이 중단되는 상황을 방지하기 위함입니다.

#### 타이머 설계

준비 카운트다운과 녹음 카운트다운 모두 `setTimeout` 기반의 재귀 호출로 구현했습니다. `setInterval`을 사용하면 탭이 백그라운드로 전환될 때 타이머 오차가 누적되는 문제가 있어 이를 피했습니다. 준비 카운트다운이 0이 되면 자동으로 녹음이 시작되어 사용자의 별도 조작 없이 흐름이 이어집니다.

#### 완료 후 피드백

발표가 끝나면 `CoachBubble` 컴포넌트가 단계별 맞춤 피드백으로 교체됩니다. 키워드 모드에서는 몇 개의 키워드를 사용했는지, 핵심 파악 모드에서는 원문 핵심을 잘 파악했는지를 시각적으로 보여줍니다.

## 4. 문제 해결 및 트러블슈팅

---

### 4.1 카운트다운 시간이 발표 녹화 데이터에 포함되는 문제

#### 문제 상황

발표 시작 전 5초 카운트다운 동안 사용자는 카메라를 응시하지 않고 화면을 세팅합니다. 그런데 녹화가 이 시점부터 시작되어 부정확한 시선·자세 데이터가 분석에 포함되는 문제가 있었습니다.

#### 원인

`LiveFeedbackTracker` 컴포넌트가 마운트되는 즉시 카메라 초기화와 녹화 시작이 함께 실행되는 구조였습니다. 카운트다운 오버레이가 화면에 표시되는 것과 무관하게 녹화는 이미 진행 중이었습니다.

#### 해결 방법

카메라 초기화(스트림 확보, WebSocket 연결, MediaPipe 시작)와 녹화 시작을 완전히 분리했습니다. `canRecord` prop을 추가하여, 부모 컴포넌트에서 카운트다운 상태와 연동해 값을 전달합니다. 카운트다운이 진행 중일 때는 `false`, 종료되면 `true`가 되어 그 시점에 녹화가 시작됩니다.

```tsx
// 카운트다운 종료 순간 녹화 시작
useEffect(() => {
  if (canRecord && streamRef.current && !mediaRecorderRef.current) {
    startRecordingFromStream(streamRef.current)
  }
}, [canRecord])
```

#### 결과와 의미

발표 시작 신호가 울린 이후의 데이터만 분석에 사용되어 분석 정확도가 개선되었습니다. 카메라 초기화는 카운트다운 중에 미리 완료되므로 사용자가 체감하는 시작 지연도 없습니다.

---

### 4.2 홈 화면 닉네임이 표시되지 않는 문제

#### 문제 상황

홈 화면 인사 문구에서 닉네임 대신 "사용자"가 표시되었습니다. 동일한 계정으로 네비게이션 바에서는 닉네임이 정상 표시되고 있었기 때문에 데이터 자체의 문제가 아님을 파악했습니다.

#### 원인

홈 데이터를 제공하는 `/personal/home` 엔드포인트가 404를 반환했고, 에러 핸들러에서 조용히 실패하면서 닉네임 상태가 초기값으로 남았습니다. `/personal/home` 응답에 닉네임 필드가 있다고 가정하고 설계했던 것이 문제였습니다.

#### 해결 방법

닉네임 fetch를 홈 데이터 fetch와 독립적인 useEffect로 분리하고, 네비게이션 바와 동일하게 `/profile/get` 엔드포인트를 사용하도록 수정했습니다. 두 API가 서로의 실패에 영향을 받지 않는 구조로 개선했습니다.

#### 결과와 의미

단순히 API를 교체하는 것을 넘어, **하나의 API 오류가 전체 화면의 다른 데이터 표시까지 막는 구조를 해소**한 것이 핵심입니다. 이후 홈 데이터 API에 문제가 생겨도 닉네임은 항상 표시됩니다.

---

### 4.3 MediaPipe 두 모델 동시 실행 시 오류

#### 문제 상황

FaceMesh(얼굴)와 Pose(자세) 두 모델을 `Promise.all`로 동시에 실행하면 WASM 모듈 충돌 오류가 발생하며 분석이 중단되었습니다.

#### 원인

MediaPipe의 FaceMesh와 Pose는 내부적으로 동일한 전역 WASM Module 인스턴스를 공유합니다. 두 모델이 동시에 같은 Module 초기화를 시도하면서 충돌이 발생했습니다.

#### 해결 방법

두 모델을 `Promise.all`이 아닌 순차 실행으로 변경했습니다. 첫 번째 모델의 프레임 처리가 완료된 후 두 번째 모델을 실행합니다.

#### 결과와 의미

순차 실행으로 변경하면 처리 시간이 늘어날 것을 우려했지만, 실제 사용에서 한 프레임당 처리 시간이 30fps 기준(약 33ms)을 초과하지 않아 사용자가 체감하는 지연은 없었습니다. **외부 라이브러리를 사용할 때는 내부 동작 원리까지 이해해야 한다**는 교훈을 얻었습니다.

## 5. 회고 및 성과

### 기술적 성장

이 프로젝트를 통해 가장 크게 성장한 부분은 **브라우저 미디어 API와 실시간 데이터 처리**입니다. React를 다루는 것에서 나아가, MediaRecorder의 생명주기 관리, AudioContext의 데이터 변환 파이프라인, WebSocket 연결 관리까지 브라우저가 제공하는 저수준 API를 직접 다루었습니다.

SVG 시각화도 처음에는 차트 라이브러리를 사용하려 했지만, 삼각형 레이더 차트처럼 라이브러리가 지원하지 않는 형태가 필요할 때는 직접 구현이 더 빠르고 정확하다는 것을 배웠습니다. 수학적 계산으로 좌표를 결정하는 과정이 어렵지 않다는 것도 알게 되었습니다.

### 협업에서 배운 것

공통으로 사용되는 컴포넌트(`PracticeLayout`, `CircleProgress`, `TimerSection` 등)를 먼저 설계해 팀원들과 공유했습니다. 처음부터 재사용을 고려해 props 인터페이스를 설계하는 것이 나중에 중복 코드를 줄이는 데 얼마나 효과적인지 직접 경험했습니다.

### 사용자 관점에서의 개선

"기능이 동작한다"와 "올바르게 동작한다"는 다릅니다. 카운트다운 중 녹화가 포함되는 문제는 기능 자체는 정상이었지만 사용자에게 전달되는 분석 결과의 가치를 떨어뜨렸습니다. 이처럼 코드 레벨이 아닌 **사용자 경험 레벨에서 문제를 발견하고 수정하는 습관**을 기를 수 있었습니다.
